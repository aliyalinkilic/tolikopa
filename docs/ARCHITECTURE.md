# Architecture

## Components

```
┌ Windows Domain (CORP) ─────────────────────────────────────────────┐
│  PC × N   → Tolikopa Agent (Go, Windows Service, LocalSystem)       │
│            GPP Scheduled Task (Update) install/update from NETLOGON │
└───────────────┬────────────────────────────────────────────────────┘
                │ HTTPS POST /api/v1/ingest  (Bearer, gzip, 60 s batch)
                ▼
┌ Ubuntu 10.0.0.10  (Docker Compose) ────────────────────────────────┐
│  caddy  :443  TLS(self-signed) · static SPA · /api,/ws reverse proxy│
│    │                                                                │
│  api    :8080  Go+Echo · ingest · REST · WS hub · alert engine      │
│    │ pgx/v5 pool                                                    │
│  db     :5432  TimescaleDB 2.27 (PostgreSQL 17)                     │
└─────────────────────────────────────────────────────────────────────┘
                ▲ browser — React SPA + live WebSocket
```

The Ubuntu server itself is also monitored, by the Linux agent build (a systemd unit).

## Data flow

1. **Collection:** the agent collects metrics at various cadences (vitals 15 s,
   disk/net/process 60 s, SMART 30-60 min, event log in real time) and accumulates them in a
   `Sample` queue.
2. **Sending:** every 60 s (or when the queue fills up) an `Envelope` is gzipped and sent to
   `POST /api/v1/ingest`. On failure it is written to `spool/` and retried later.
3. **Ingest:** the API validates → `machine`/`machine_live` upsert → network delta (boot_time
   reset) → process name is resolved to a category → bulk write to
   `metric_sample`/`disk_usage_sample`/`process_sample`/`event` (`COPY`/multi-INSERT,
   `ON CONFLICT DO NOTHING`).
4. **Derivation:** a background job (30-60 s) evaluates the alert rules and updates the
   `usage_session` (active-usage sessions) table. Continuous aggregate policies refresh the
   rollups.
5. **Presentation:** the panel's live view comes from `machine_live` + WebSocket; history charts
   come from the continuous aggregates (`metric_5m/1h`, `net_user_1h`, `proc_cat_*`).

## Why these choices

- **Go agent:** a single static `.exe` with no .NET/Python runtime dependency → painless GPO push,
  small footprint, a real Windows service.
- **TimescaleDB:** compression and continuous aggregate rollups for time-series metrics. The volume
  of 50 machines × 30 s is small; the real gain is compression + ready-made rollups. (Toolkit
  functions are not used in the core.)
- **`machine_live` hot table:** the live read path never touches a hypertable → the panel is always
  fast.
- **Caddy:** brings TLS (the self-signed, non-CA certificate generated by `setup.sh` — rationale:
  SECURITY.md → TLS), static SPA serving and the reverse proxy together in one place.

## Ports / network

| Port | Service | Access |
|------|---------|--------|
| 443  | Caddy (panel + API + WS) | whole LAN |
| 8080 | API | compose internal network only |
| 5432 | TimescaleDB | compose internal network only |

Agent → server uses 443/TCP only. Caddy applies a LAN IP allowlist + rate limit to
`/api/v1/ingest`.

## Scale assumptions

50 machines × 30 s: `metric_sample` ~144k rows/day, `process_sample` (top-10) ~1.44M rows/day
(~2-4 GB/year after compression). A single node is sufficient.
